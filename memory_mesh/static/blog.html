AGENT MEMORY AND COORDINATION

The second investigation should start smarter.

How Mesh uses FalkorDB to give a small team of specialist agents persistent, shared memory.

Technical project story·Incident Response Memory Mesh

Imagine investigating the same kind of security alert for the third time this week. The first investigation uncovered a useful pattern. An analyst approved a response. Yet the next investigator starts with an empty page and repeats the work.

That is the problem Mesh explores: how can agents carry useful knowledge between investigations, share it with one another, and show where that knowledge came from?

Mesh is a local demonstration built for the Agent Memory and Coordination hackathon track. It models a small incident-response team with three specialist workers. The workers are deterministic Python functions, and their shared operational memory lives in FalkorDB.

A memory loop, not a one-shot answer

The demo begins with a report such as “Repeated login failures for an admin from a suspicious IP and shared device.” Triage classifies it and hands it to an investigator. The investigator searches tenant-scoped memories, records an episodic account and a semantic pattern, then hands findings to response. Response suggests an action for an analyst to review.

If the analyst approves the recommendation, Mesh stores a procedural memory. When a similar report arrives later, the investigator can retrieve that procedure and the earlier case that produced it.

Incident→Triage→Investigator→Recall→Response→Analyst decision

Why use a graph for this?

A collection of notes can tell us what was remembered. A graph can also show how each record relates to the work that produced or reused it.

IncidentHAS_HANDOFFHandoffRECALLED_INMemory
Every memory can be traced back to its source incident; every handoff keeps its owner, task, findings, and lifecycle.

Mesh stores incidents, memories, agents, handoffs, audits, and analyst decisions as tenant-scoped nodes. Edges capture relationships such as DERIVED_FROM, FOR_INCIDENT, CREATED, RECALLED_IN, and ABOUT. That provenance is the difference between “the system returned a note” and “the system can show why this note is part of this investigation.”

FalkorDB is part of the workflow

FalkorDB is the production source of truth in Mesh. The application reads and writes incidents, memories, handoffs, audits, decisions, dashboard data, and history through graph queries. Startup requires FalkorDB; an unavailable graph produces a clear startup error. SQLite is used only by tests that explicitly construct the test backend.

MATCH (m:Memory)-[:DERIVED_FROM]->(i:Incident)
WHERE m.tenant_id = $tenant_id
  AND i.tenant_id = $tenant_id
  AND i.id = $incident_id
RETURN m, i

The investigator currently uses explainable keyword overlap rather than embeddings. It ranks matches using shared words, memory-type priority, stored confidence, and a small same-user relevance boost. That keeps the demo inspectable while making clear that the score is a heuristic, not a calibrated probability.

Coordination records that survive a refresh

The workers run sequentially in one process. Their handoffs are still persisted as graph records with a simple lifecycle:

pending→claimed→completed

This lets someone inspect which worker owned a task, what findings were passed, and when the handoff changed state. The RECALLED_IN edge records which memories the investigator used. Audits record important events, and the analyst decision is represented as its own graph node.

The honest boundary

Mesh is a prototype for exploring agent memory, not an intrusion-detection product. It does not call an LLM, inspect live telemetry, or execute mitigations. The sample incidents are synthetic, and approval means an analyst accepted a simulated recommendation.

Try the memory loop

  1. Open the live Mesh demo and create a fresh workspace.
  2. Run the admin-login scenario and inspect the three agent outputs.
  3. Approve the simulated recommendation to save a procedural memory.
  4. Run the scenario again and follow the recalled memory back to its source incident.
  5. Refresh the page or switch workspaces to see persistence and tenant-scoped results.

The second run is the heart of the demo. It makes the central question observable: can an agent team carry forward useful experience, and can a person trace that experience back to its source?

What comes next

The next engineering steps are to evaluate recall against labeled synthetic cases, make handoff recovery robust to interrupted workflows, and add real authentication before connecting a multi-user environment. A future worker could use an LLM, but its memories and decisions should still carry provenance and remain reviewable.

Mesh takes a deliberately small step toward agents that remember: persist the work as a graph, make handoffs visible, and let the next investigation benefit from what the previous one learned.
